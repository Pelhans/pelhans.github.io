# 模块定位

从Query中识别出where以及what部分，然后将where部分进行地址POI召回。

难点与挑战:

1.  语义模糊，例如在上海搜索"龙之梦酒店"，切分成where+what，或者整体作为一个what，结果差异很大（需要召回后再判定，本小节不详述）；
2.  多业务交叉，有些供给的起名和地标很像（名称比较随意），问题复杂度就很高
3.  外部知识缺乏：where-what 的在中长尾数据上，严重依赖外部知识来判断它到底是个什么？
4.  性能问题，由于wherewhat信号需要传给实体链接和地图召回，因此性能要求极高，整个模块不能超过2ms；

# 迭代路径

传统的NER信号拼接 -> CNN-CRF -> BERT-CRF(蒸馏V1) -> BERT+CRF(蒸馏V2) -> 大模型的应用

# 样本构建

wherewhat主要通过以下方式获取 620w 高质量标注数据，平均长度 7.12：

1.  自动构建数据集（简单数据 + 中等数据）（500w条，准确率 95%）：

1.  接加地图的地址类 POI 数据做纯 where
2.  商户/商品数据做纯 what
3.  纯 where 同时加上各类高频what进行组合得到符合类数据；
4.  当前线上识别出地标，且主点点击率较高的，比如点击率高于同类型均值 0.1 的
5.  没识别到地标且用户session 内没搜索类似的词，则认为是纯 what

2.  人工标注（得到标注数据 100w 条，准确率 92% 以上）：

1.  当前线上识别出地标，且主点点击率低于均值的
2.  没识别到地标但用户session 内搜索类似的词出了地标，则让人工去标注
3.  初版模型打分在 0.4-0.6 之间的数据，送人工标注

3.  根据 badcase，针对逆序类问题、医药类商品、短 query等问题进行针对性标注，得到数据 20w 条，准确率 92% 以上。

# 模型训练

CNN + CRF 模型 -> BERT（蒸馏）+CRF-> 优化蒸馏效果 -> 基于大模型检索增强的模型迭代。

## CNN + CRF

### 模型结构

嵌入向量（用的腾讯向量作为初始向量，而后取训练数据集中出现的词作为线上词表） -> CNN层1（3个1维 kernel）-> 结果 concat 一起 -> 一个 CNN 层2（kernel 1，3，5）-> concat在一起 -> FN -> CRF

### 模型训练

embed 维度 100d， 3个 kernel，分别是 1，3，5 。

标签 5 个（B-where、I-where、B-what、I-what、O）

### 效果

where f1 78.29、what f1 94.13

## BERT + CRF V1（蒸馏）

见 [DistilBERT](https://www.yuque.com/yuqueyonghuyit3fz/nssocf/mpito3smsbkm3vbo)

3 层BERT，384 维隐层，在线调用

重点是怎么蒸馏到了小 bert 上。蒸馏方案为

1.  这一版仅蒸馏的 logits，用的 distilBERT。从 24 层 BERT 蒸馏到 3 层， 1024 维到 384 维。head 数量还是 16 没变。
2.  参数量从 340M 变为 16.8 M（(12\*384\*384)\*3+ 30000\*384 = 16.8M)，其中 vocab 大小 3w
3.  先在通用任务上进行的蒸馏，而后在 where-what 数据集上又蒸馏了一次

1.  通用任务上蒸馏是 logits 的 MSE loss 和 最后隐层输出的 loss 还有 MLM 的 loss
2.  专有任务上的蒸馏，就是 where-what 后面 CRF logits 的 MSE loss 和 CRF 前 FFN logits + gold 标签的 loss

4.  通用任务的数据来源是什么？

1.  酒店领域数据（UGC 数据、酒店页面信息(酒店介绍，酒店poi/goods 信息, 酒店领域报告)
2.  通用领域数据（百度百科网页数据和维基百科文本数据）
3.  二者混合，通用：领域为 1：1
4.  整体数据量 2.5 亿(0.25B) 数据，单卡，一个 epoch 是一个半点，训练了100 个epoch，训练了一周。

5.  where-what 任务上，数据量是 600w 条，平均长度7，所以是 420M 数据，训练了 20 个epoch

1.  先微调了 bert-large - CRF
2.  而后再蒸馏到小模型上

6.  效果保持率：蒸馏前 BERT 微调后的效果为 87.09%，蒸馏后是 84.63%
7.  速度上，相比于 bert large，快了20多倍

## 优化蒸馏效果 BERT + CRF V2

### 阶梯式蒸馏 + 多层蒸馏

从 24 层 BERT 蒸馏到 3 层 BERT 的效果下降较快，根据研究，通过选取多个助教进行阶梯式蒸馏可显著提升蒸馏后的模型效果。

另一方面，tinybert 的对中间结构进行蒸馏也被证明可有效提升蒸馏后的模型效果，因此考虑将二者结合，提升蒸馏后模型的效果

蒸馏方案：

1.  挑选多个助教模型

1.  24 主教师网络 + 12 层的助教(768) + 6层的助教(768) 来蒸馏到3层的学生上
2.  为什么挑选了这三个，而不是其他模型（现成的模型，并且多层蒸馏要有整数对应关系，所以这么选比较合适，都是3的倍数）

2.  数据上有变化么？

1.  加入了更多的数据：在通用数据上加了很多商家/地址类数据。数据量扩充到了1B，十二张卡微调了两周。

3.  多个助教怎么用？

1.  都作为教师，分别和学生模型去算 MSE loss，然后加和平均，模型越小，loss 占比越低

1.  $Loss = L_{24} + \frac{1}{2}L_{12} + \frac{1}{4}L_{6}$

2.  为什么这么设计：模型越小，它的输出准确率相对越低，loss 比例一致验证过效果不好。最终根据手拍定了这个数。资源有限没有做更多查找。

4.  多层蒸馏是怎么搞的？

1.  参考了 tinyBERT。蒸馏了 attention 和 FFN + embedding + FFN + logits

5.  助教训练了么？

1.  整体训练和一期是一致的，先通用领域对小模型一起蒸馏。然后教师网络和助教网络一起微调，最后再蒸馏。

6.  效果保持率：蒸馏前 BERT 微调后的效果为 87.09%，蒸馏后是 86.18%。相比于上一版

## 基于大模型RAG的训练数据增强（大模型蒸馏）

### 任务背景

目前，我们拥有6M的训练数据。但随着优化进入长尾阶段，需要更多的难样本来提升模型在长尾段的识别能力，而人工标注成本高周期长，因此决定引入大模型来对数据进行标注，提升数据集质量和中长尾数据的数量，覆盖长尾的数据 pattern。

### 模型选取

对比了 GPT4、claude v2 和 Qwen-72B-Chat 三个模型。选用 30 个线上提报的难 case。结果如下

-   gpt-4: ，type error: 0，准确率 100%
-   Qwen-72B-Chat: type error: 4，acc 86.7%

可以看高 gpt 4 效果最好，Qwen 差一些。整体来说还是世界知识不足导致的，指令遵循程度都是够的，因此选择 RAG + Qwen 72B 的路线，提升离线数据质量。

### RAG 构建

#### 召回

对每个 query ，为模型提供：

1.  字符串文本召回，各取 top 10

1.  NER 片段召回
2.  cnn-crf 输出的 where-what 召回
3.  全 query 召回

2.  向量召回结果，各取 top 10

1.  cnn-crf 输出的 where-what 召回
2.  全 query 召回

3.  召回源包含 POI、商品、品牌、标签 数据

取这个50 个结果的名字、地址、后台品类信息。对返回的结果进行融合，并记录结果重复出现的次数和位置，取top 5个结果送入大模型。

#### 送入大模型

由于业务规则复杂，所以需要大量独立的prompts来处理不同的query。如果每个query都结合着全部prompts去做推理，那么将成本会比较高，错误率有可能会增加。

参考策略：[Tactic: Use intent classification to identify the most relevant instructions for a user query](https://platform.openai.com/docs/guides/prompt-engineering/tactic-use-intent-classification-to-identify-the-most-relevant-instructions-for-a-user-query)。将复杂任务拆分成更简单的子任务，分阶段多次递归地发起请求。即先对query的类型进行分类，并利用该分类来确定query需要哪些prompts。

prompt 如下

```c
假如你是一个专注于本地化生活服务的智能搜索引擎，您的任务是运用先进的语义理解和句法分析技术，并结合下述的6种业务规则和2种标签规则，准确识别出用户查询中的用户需求"What"和位置信息"Where"。
请注意，由于业务规则的复杂性，这项任务具有较高的难度。我们鼓励您在提供答案前仔细思考并逐步推敲。
6种业务规则如下:
Category_1: 服务/商品/商家类的单成分查询，且无明确的位置信息。注意: 单独的酒店名、影院名应该属于该类别。
意图分析: 用户寻找特定商家、特定服务或特定商品，而非寻找特定地理位置的信息。这种情况下，用户需求"What"是该查询中的服务/商品/商家，位置信息"Where"是null。该类别的Category是1。
常见的示例如下:
"上门开锁"属于'纯服务名'。意图分析: 用户希望找到"上门开锁"(服务)这项服务。结果: ("What": ["上门开锁"], "Where": null)

"昆泰酒店"属于'纯商家名'。意图分析: 用户希望找到"昆泰酒店"(商家)这个商家。结果: ("What": ["昆泰酒店"], "Where": null)

"北京美嘉欢乐影城三里屯店"属于'纯商家名'。意图分析: 用户希望找到"北京美嘉欢乐影城三里屯店"(商家) 这个商家，隐含的地理位置信息"三里屯"只是商家分店名一部分，不能将其识别为位置信息"Where"。结果: ("What": ["北京美嘉欢乐影城三里屯店"], "Where": null)

"西湖龙井茶"属于'纯商品名'。意图分析: 用户希望找到"西湖龙井茶"(商品)，隐含的地理位置信息"西湖"是商品名里固有部分，不能将其识别为位置信息"Where"，而是应该将其视为整体用户需求"What"的一部分。结果: ("What": ["西湖龙井茶"], "Where": null)
"苹果充电器快充1米"属于'纯商品名'。意图分析: 用户希望找到"苹果充电器快充1米"(商品)。结果: ("What": ["苹果充电器快充1米"], "Where": null)
"白云山夏桑菊颗粒20袋"属于'纯商品名'。意图分析: 用户希望找到"白云山夏桑菊颗粒20袋"(商品)，隐含的地理位置"白云山"是商品名里的固有部分，不能将其识别为位置信息"Where"，而是应该将其视为整体用户需求"What"的一部分。结果: ("What": ["白云山夏桑菊颗粒20袋"], "Where": null)
Category_2: 无明确的方位词下，商家+服务/商品类的多成分组合查询。由于这类查询没有明确的方位词(如"附近"、"周边")，所以为了确定是否需要将商家名识别为位置信息"Where"时，首先需要判断商家类型与服务/商品类型是否属于供给关系，这依赖于强大的先验知识，需要认真思考。
意图分析: 由于无明确的方位词，所以需要进一步判断商家类型与用户寻找的是特定服务/商品类型之间是否属于供给关系，而供给关系可以分为以下的3类情况。
第一类情况，商家类型与服务/商品类型属于明确的供给关系。如果你认为它们属于明确的供给关系，那么用户需求"What"是该商家+服务/商品的组合，位置信息"Where"是null。该类别的Category是2。

第二种情况，商家类型与服务/商品类型属于确定的非供给关系。如果你认为它们属于明确的非供给关系，那么用户需求"What"是该服务/商品，位置信息"Where"是该商家名，即使它不是地标类型。该类别的Category是2。
常见示例如下(第二种情况):
"如家酒店北京鸟巢店小龙虾"属于'商家+商品'的组合。意图分析: "如家酒店北京鸟巢店"(商家名)属于酒店，而"小龙虾"(商品)属于食物，两者属于明确的非供给关系，所以用户是希望在"如家酒店北京鸟巢店"(商家名)附近搜索"小龙虾"(商品)，而隐含的地理位置信息"北京鸟巢"只是商家名的一部分，不能单独视其为位置信息"Where"。结果: ("What": ["小龙虾"], "Where": ["如家酒店北京鸟巢店"])
"沐足万达国际影城"属于'商家+商品'的组合。意图分析: "万达国际影城(商家名)属于影院，而"沐足"(服务)属于非影院可提供的服务，两者属于明确的非供给关系，所以用户是希望在"万达国际影城"(商家名)附近搜索"沐足"(服务)。结果: ("What": ["沐足"], "Where": ["万达国际影城"])
第三种情况，商家类型与服务/商品类型属于模糊的供给关系。如果你无法做出准确的供给关系的判断，那么用户需求"What"是该商家+服务/商品的组合，位置信息"Where"是null。该类别的Category是2。
常见示例如下(第三种情况):
"广州酒家荔湾店莲蓉包"属于'商家+商品'的组合。意图分析: 用户希望找到"广州酒家荔湾店"(商家)售卖的"莲蓉包"(商品)，它们可能属于供给关系，无法做出准确判断，而隐含的地理位置信息"荔湾"只是商家名的一部分，不能将其识别为位置信息"Where"。结果: ("What": ["广州酒家荔湾店", "莲蓉包"], "Where": null)
"美甲海底捞望京店"属于'商家+服务'的组合。意图分析: 用户希望找到"海底捞望京店"(商家)提供的"美甲"(服务)，它们可能属于供给关系，无法做出准确判断，隐含的地理位置信息"望京"只是商家名的一部分，不能将其识别为位置信息"Where"。结果: ("What": ["海底捞望京店", "美甲"], "Where": null)
Category_3: 存在明显的方位词下，商家+商品/服务类的多成分组合查询。这与Category_2的主要区别在于这类查询存在明确方位词(如"附近"、"周边")，包含了对特定地理位置的需求，因此无需考虑供给关系，商家名被直接标记成"Where"，无论它是否属于地标类型。
意图分析: 用户使用了明确的方位词来指示搜索引擎寻找某个特定商家附近的服务或商品。这种情况下，用户需求"What"是该查询中的商品/服务，位置信息"Where"是该查询中的商家。该类别的Category是3。
常见的示例如下:
"必胜客望京店隔壁的美甲"属于'商家+方位词+服务'的组合。意图分析: 用户希望在"必胜客望京店"(商家名)的"隔壁"(方位词)找到"美甲"(服务)。这种属于特殊情况，商家名需要被标记成"Where"。结果: ("What": ["美甲"], "Where": ["必胜客望京店"])
"美食水晶国际酒店周边"属于'商家+方位词+服务'的组合。意图分析: 用户希望在"水晶国际酒店" (商家名) 的"周边" (方位词) 找到"美食"(服务)。这种属于特殊情况，商家名需要被标记成"Where"。结果: ("What": ["美食"], "Where": ["水晶国际酒店"])
"海底捞附近蛋糕"属于'商家+方位词+商品'的组合。意图分析: 用户希望在"海底捞" (商家名) 的"附近" (方位词) 找到"蛋糕"(商品)。这种属于特殊情况，商家名需要被标记成"Where"。结果: ("What": ["蛋糕"], "Where": ["海底捞"])
Category_4: 地标类单成分查询，且无明确的需求。注意: 单独的酒店名、影院名不属于该类别，而是属于Category_1。
意图分析: 用户探索某个具体地标附近的各种信息和推荐，而没有明确的需求指向特定的商家、服务或商品。这种情况下，用户需求"What"是null，位置信息"Where"是该查询的地标成分。该类别的Category是4。
常见的示例如下:
```

# 问题

1.  什么是 where-what

1.  识别出 query 中的地址成分和非地址成分。地址成分在召回时会被移除编程经纬度画圈，非地址成分走文本或者id召回

2.  高德也有 where-what么？或者说 where-what 是一个通用任务么？

1.  也有，不过具体的定义不一样，他们的更像美团地图那种，where 是核心地址成分，比如 望京东路8号，what 是 8 号

3.  为什么要有 where-what？直接用 NER 不行么？

1.  最开始尝试过用 NER 做，但是

1.  where-what 是和业务强绑定的，如酒店业务里，到综供给就是 where，这种随业务变化的特性和地图对所有业务一致的定义区别较大
2.  where 是一个相对概念，如昆泰酒店附近 KTV，昆泰酒店此时就是地标，要出 where，但是对于 NER 它就一直是一个 POI，我们需要在 NER 后做很多的规则来覆盖各种场景，最终准确率还不高。所以不如搞一个地标专用的 where-what 序列标注

4.  where-what 和地址元素解析的区别，你们有地址要素解析么？

1.  没有做地址元素解析。做地标识别不需要那么细粒度的结果。期间倒是想过用地址元素解析来作为特征，但是最终试下来没有用词表 NER 的效果好。。。

5.  美团地图有没有 where-what，为什么没用他们的？

1.  同问题2

6.  是一个什么任务？标签有几种？为什么没有设置更细粒度的？

1.  序列标注任务，标签有 3 大类, where、what、Other 三类，每个还有 B 、I 两个

7.  where-what 随不同业务的区别输出是怎么做到的？

1.  大模型小模型，先以大搜为基准，对大家共识的地址成分进行识别，再针对每个业务做小模型适配，输出业务特定的 where-what

8.  做 where-what 的难点是什么？​

1.  多业务交叉，供给量大，需要更多的业务知识进行识别
2.  用户 query 量大，query 的模式多，一般的模型很难覆盖好长尾情况
3.  耗时要求高，只有几毫秒的时间

9.  为什么没有尝试加入知识的方案 ，比如 FLAT？

1.  主要原因：供给过多，有 POI 信息1.2 亿，deal类10亿+，词表匹配会消耗大量容量和算力
2.  尝试过 FLAT在供给少一点的业务上，但效果不好，而且耗时增加了很多。最终选择增大模型容量来提升效果。
