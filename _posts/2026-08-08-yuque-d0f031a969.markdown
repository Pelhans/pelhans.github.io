# 实体链接信号

NLP 中心之前维护的，基于 mention 的召回。有数据量 2100w

1.  实体链接的 2157.5161 w 条数据看着不少，为什么还是不够用？

1.  从底层数据库量上来看，商户数据占比较高，达到了 72.7%，再加上标签等非地标类型，整体非地标类型占比达到了 80%，因此实际数据量并不是很充足，应对高频 query 可以，但中长尾实际还是不足
2.  从top1召回率上看，实体链接的 指标为 72%，不能满足实际需求
3.  从可维护性上看，实体链接自从 21 年后，处于无人迭代状态（只保证服务不蹦）。因为 mention 停止挖掘，准召率在逐渐下降

因此自从我接手后，将识别主要依赖源从实体链接切换到 EL + 地图 + 自建 BS 召回三路上

# 美团地图召回

美团地图召回基于字符串匹配召回。且一直长期有人维护，因此是切换的主要目标源。

但有一个比较严重的问题是美团地图主要为外卖提供服务，因此它的排序结果与主搜需求差别较大，比如用户输入北京大学，排名第一的可能是北京大学东门 这种点外卖常见的点。

因此会在高频类型和高频流量上，倾向于使用 EL 结果，中长尾上使用美团地图结果。

# 自建 BS 向量召回

用于搞离线了，对于地图返回无结果或者相关性过低的，用自建召回构建离线缓存结果。

除了上面的两个召回源，还有一个小的自建 BS向量召回。用于解决字符差距过大，需要语义召回的场景。

基础数据源是地图维护的 poi 数据表，每天通过离线任务更新发生变化的 doc 。每日变化量 < 100w （主要是商户变化比较大）

-   你的 embedding 是怎么做的？用自训练 bert 做的 embedding

-   训练数据采用 query + 经纬度geosh6 -> poi\_name + address + 品类 + geosh6
-   负样本分为两块：

-   简单负样本：batch 内负采样，batch 采用 1024 大小
-   中等难度负样本：用 自建 ES 召回，得到相关性排名10-20 名的结果作为中等难度负样本 取 20 个
-   难负样本：采用大搜人工定期标注的体验标注（每周1w条）数据中召回但被标注为不相关的 poi，每个 query 最多 5个

-   正样本：

-   用户搜索 query 时，有下单的 poi 作为正样本
-   用户搜索 query 时，有下单时的地标主点作为正样本
-   最终中等 + 难负样本 和正样本比例是 1：5

-   样本怎么结合使用的？

-   就混在一起

-   训练分为两阶段：

-   第一阶段是类似 simcse 的方案，正样本是 dropout 的，负样本是 batch 内负采样
-   第二阶段是中等样本+ 难样本 + 正样本去 微调训练

-   效果是怎么评估的

-   看召回的 hitrate
-   这个 hitrate 是 93%

-   BERT 具体参数：

-   6层小 bert

-   为了省时间，EL 召回tp999 15 ms 。我这个算上 RPC 比这短（具体多少？）

-   query 长度32
-   doc 侧预先 embedding 好，长度比较短，约 256

-   最终这一路召回 10 个结果，附带各种信息。与其他路召回一起进行混合排序
