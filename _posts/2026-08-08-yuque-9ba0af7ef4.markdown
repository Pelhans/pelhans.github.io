## 1\. 关联 Query 挖掘

生成式推荐怎么结合？

### 1.1背景

从功能上看，快捷指令功能旨在提高用户搜索/下单效率，这通过对用户 query 进行 修正（如改写）、平移（丽枫->如家）、泛化（电竞三人间—>电竞房）、细化（电竞房->电竞双人间） 四种修改实现。同时也可以配合公司经营政策如低价（推荐更容易成单的低价酒店）。也可以实现商户的推荐（对报名特殊活动的商户进行提权推荐）。

从流量上看，酒店频道内的用户搜索请求平均长度为6.2，整体搜索无结果率约 3.2%，意图不明请求 qv 占比 3.69%。这些 query 即使在用户换词后的访购率也远低于正常请求，说明用户不能很好的使用美团功能，不知道如何寻找自己心仪的酒店。

### 1.2 方案概览

加一个架构图

-   离线模型训练（数据选取 + 样本构建 + 模型选取 + 模型训练 + 模型评测）
-   线上部署

-   怎么部署的（用的什么方案，速度怎么样？怎么提升速度）

-   怎么保证生成的质量（线上benchmark 质检 + 外包抽样回测 + sakos 风险检测 + 多路召回检测（保证有结果）

### 1.3 离线模型训练

### 1.3.1 任务定义

首先是下游任务定义，大框架上来说是 query 推荐，实际上包含一下八类任务

-   平移
-   同义词推荐（秋千床 -> 吊床）
-   同品类词推荐（五星酒店 -> 豪华酒店、全季酒店 —> 如家酒店）
-   修正
-   输入错误修正
-   拼音输入转汉字（hanting -> 汉庭）
-   输入错误（鹿枫-> 麓枫酒店
-   丢词（皇姑区苍山路311第六单元601-> 皇姑区苍山路31号311）
-   城市修正
-   六约地铁站3号龙岗线（惠州）-> 六约地铁站3号龙岗线（深圳）
-   泛化
-   sm主题 -> 情趣房、电竞酒店4080 -> 电竞酒店配置好
-   细化
-   主题房 -> 情侣主题房 、 电竞主题房

### 1.3.2 数据选取

对每个下游任务都构造相应的数据集

-   平移任务
-   同义词推荐：
-   标签同义词：使用酒店图谱数据中，标签的别称数据构造 pair （海边酒店 -> 海景房），抽取 XX 条数据
-   酒店别称/地点别称：使用地图侧维护的 poi 别称数据构造 pari（滨河西里南区->铁十六局家属楼），抽取 XX 条数据
-   同品类词推荐：
-   按照请求类型，在用户换词session 中，按照意图关联相应同品类 标签 / POI 数据
-   标签同品类：看标签所在的索引字段，推荐相同索引字段数据，抽取 XX 条数据
-   酒店同品类：有星级/均价字段，推荐价格/星级类似的热门酒店，抽取 XX 条数据
-   其余 POI：推荐相同三级品类（最细粒度）的、相似热度的 POI，抽取 XX 条数据
-   修正任务
-   输入错误修正：使用线上改写词表数据，按照错误类型，每种类型抽取 XX 条数据
-   城市修正：使用线上异地信号模型打分，结合地标信号全国识别结果top5 ，得到高质量需要切换城市的数据（异地直跳信号没跳的可以尝试推荐），抽取 XX 条数据
-   泛化任务：
-   使用酒店图谱数据，将该标签的上级节点数据，抽取 XX 条数据
-   细化：相反的取，抽取 XX 条数据

### 1.3.2 数据构建

采用 alpca 格式，分为 instruction、input、output 三个，样例如下

```json
{
  "instruction":"你是一个搜索系统专家，熟悉用户搜索词所表达的真实需求，包括购买意图、对商品/商家 等规格/型号/价格等细分属性的确切需求，以及不同表述之间的关联和区别。 需要你判断搜索词变更后进行搜索是否会出现不符合用户需求的结果，要求：1. 相同商品/商家、修饰词的不同说法是可以的，也可以用“下位词”替代，这些词的搜索结果属于原词的子集，可以全部满足用户要求；2. 品牌词、专有名词不能改变，如果发生改变、缺失则搜索结果可能包含其他品牌的商品，导致出现不符合用户需求的结果；3. 价格、属性等表述不能丢失，尤其是数字类型的说法，如果发生缺失或过度改写，搜索结果可能与用户要求出现不一致，不符合用户需求；4. 不能替换为“上位词”，这样通常会搜索得到范围广的结果，其中会有很多不符合用户的需求。请按照格式依次回答下面的问题。1. 用户搜索 秋千床 时，他想要什么？2. 基于该query，有效的query 扩展有哪些？请按照可能性进行排序。",
  "input":"",
  "output":"1. 用户搜索“秋千床”时，他是要寻找提供带有秋千床或者类似吊床设施的酒店。 2.按照可能性排序，可能的扩展有 吊床房、秋千房间、露台吊床、房内秋千等。"
}
```

最终数据量为 1w 条。

整体采用单步 COT 的 prompt（格式为任务定义、query1 含义、query1 的扩展有哪些，哪些最可能作为有效扩展）

## 1.5 怎么保证生成质量

1.  上线前 benchmark 指标判断
2.  线上运行时，checklist 监控
3.  定期外包抽样回测，发现线上问题
4.  调用美团 sakos 风险检测，对有风险 query 进行过滤/无害 query 替换
5.  多路召回检测（保证有结果）

1.  模拟调用召回，保证有结果
2.  为了减少调用，采用一些优化策略：

1.  加了缓存，针对候选词和已经被搜索过的词的召回结果数进行了缓存，因此实际新增 QPS 约为 XX
2.  对于不在缓存里，但相比于有结果 query 变短的，可以不进行调用（有结果是指其他路召回的）

  

## 2\. 其他渠道挖掘的关联 Query 过滤

相关性判别（广义上的）比如搜索一个200元的酒店，可以推荐全季酒店

与 Query 推荐任务类似，只是在数据构建时加入负样本。并且更改 prompt 形式。其中：

1.  负样本来源：负样本采用 batch 内采样，通过构建 ES 服务得到有字符相关性但相关性小于指定阈值的（酒店频道内相关性模型）。并通过外包进行筛选，移除过于明显的无关负例
2.  修改 prompt 形式
