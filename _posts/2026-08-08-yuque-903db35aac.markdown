# 背景

为什么要做？

地标下的排序是对多个召回源返回的结果，根据美团大搜 / 各下游业务场景进行适配，得到对每个业务最适合展示的 top1 地标。举个例子，比如 用户搜索长白山，在美团大搜显示长白山景区这个点。在外卖频道内，排在第一的事长白山大酒店，在酒店频道内会展示多个区域 id ，而不是一个地标点。

主要挑战是啥

1.  性能要求高，前面说过，地标 tp99 为 12ms。平均耗时为 5ms。所以均摊到每个模型上的时间非常短
2.  准确性要求高：与高德不同，高德可以展示多个主点供用户选取，而美团只会展示一个主点给用户，因此对top1结果的准确率要求更高

基于以上两点，需要得到一个耗时短，准确性高的模型（冲突的）。

繁荣度是怎么计算的？

出发点：传统的基于美团用户行为的热度统计方案只能覆盖 2000多万的 poi，相比于地图 1.12 亿的总量来看有比较大的 gap，因此如何让剩余的 9000w poi 有热度信息是需要做的事，否则就会出现因为没有热度，导致新开业商场排在后面的情况。

![image.png](/img/yuque/NEXT/3._地标业务/1._地标信号识别/assets/1.3_排序优化-1.png)

大搜地标识别的目的是为了展示周围商家，因此一个 POI 周围 poi 的数量可以一定程度体现该区域的繁华程度，可以看做地标热度的一种展现形式。

周围商家的定义为距离当前 poi 4km 以内的 poi（对应当时大搜的召回半径）。为了快速进行召回，这里采用了地理位置分桶的方式将 poi 划分到一个个小块中，最终通过遍历 poi 对应块以及周围的 8 个块来做召回，并结合距离卡控得到周边poi。

地理位置编码最开始考虑了两种方案，分别是 geo hash 和墨卡托编码分桶，但 geohash 的计算量相对较大，且容易出现 geohash 相近的 poi 可能实际距离很远的情况，因此最终采用墨卡托编码分桶的方式。其中墨卡托投影的原理详见 [墨卡托投影坐标系（Mercator Projection）原理及实现C代码](https://www.cnblogs.com/DHUtoBUAA/p/6706642.html)。对经纬度进行墨卡托编码，而后根据自己设定的缩放级别（我这里设置的是7，对应的就是一个小块边长 1.22km）进行线性投影分桶，得到经纬度对应的块。

![image.png](/img/yuque/NEXT/3._地标业务/1._地标信号识别/assets/1.3_排序优化-2.png)

```c
# 预先计算好的 zoom 7 结果
zu_7 = [1222.99245234375, 1222.99245234375]
def get_zoom_utils(zoom):
    # zoom 是地图缩放级别，越大越细致
    if zoom == 7:
        return zu_7
    zu = [0,0]
    a = math.pow(2, (18-zoom))
    zu[0] = 0.5971642833709717 * a
    zu[1] = 0.5971642833709717 * a
    return zu

# 经纬度转墨卡托
def lon2marc(x,y):
    xx = x/180*20037508.3427892
    yy = math.log(math.tan((90 + y) * math.pi / 360))/(math.pi / 180)
    return xx, yy * 20037508.34 / 180

# 分桶
def smarc2region(marc_lon, marc_lat, zoom=7):
    # zoom 7 对应 2048m, 8 是 1024 m
    x = marc_lon - 20037508.3427
    y = -20037508.3427 - marc_lat
    zu = get_zoom_utils(zoom)
    bx = -int(x/zu[0])
    by = -int(y/zu[1])
    return bx, by
```

最终得到有繁荣度的 poi 1.06 亿条数据

## 版本4：基于 BERT 的finetune + 离线缓存相关性特征

为了补充 XGB 模型的语义相关性特征，同时又受限于整体耗时的限制。因此采用离线训练 BERT 模型并将query 和候选 poi 的相关性进行 squirrel 存储的方案，在收到用户请求时，即调用缓存得到 query 和 poi name的 bert 相关性分数。

BERT 模型的微调训练。

整体还是两阶段，第一阶段是无监督对比学习，正样本是 dropout 得到的，负样本全局随机负采样。

第二阶段是有监督对比学习。这块后面要好好整理一个text embedding 的东西。

主要迭代点有三个：

1.  数据样本增强：由于相关性模型的训练基于搜索用户行为标注的弱监督数据，我们结合业务经验对数据做了去噪和数据映射。为了更好的评价相关性模型离线效果，我们构建了一套人工标注的Benchmark数据集，指导模型迭代方向。
2.  BERT领域适配：美团业务场景中，Query和Doc以商户、商品、团购等短文本为主，除标题文本以外，还存在商户/商品描述、品类、地址、图谱标签等结构化信息。我们首先改进了MT-BERT预训练方法，将品类、标签等文本信息也加入MT-BERT预训练过程中。在相关性Fine-tuning阶段，我们对训练目标进行了优化，使得相关性任务和排序任务目标更加匹配，并进一步将两个任务结合进行联合训练。此外，由于BERT模型前向推理比较耗时，难以满足上线要求，我们通过知识蒸馏将12层BERT模型压缩为符合上线要求的2层小模型，且无显著效果损失。
3.  排序模型优化：给定<Query, Doc>，我们将基于BERT预测的Query-Doc相关性分数作为特征用于地标排序模型的训练中。

数据增强

BERT Fine-tuning任务需要一定量标注数据进行迁移学习训练，美团搜索场景下Query和Doc覆盖多个业务领域，如果采用人工标注的方法为每个业务领域标注一批训练样本，时间和人力成本过高。我们的解决办法是使用美团搜索积累的大量用户行为数据（如浏览、点击、下单等）， 这些行为数据可以作为弱监督训练数据。在DSSM模型进行样本构造时，每个Query下抽取1个正样本和4个负样本，这是比较常用的方法，但是其假设Query下的Doc被点击就算是相关的，这个假设在实际的业务场景下会给模型引入一些噪声。此处以商家（POI）搜索为例，理想情况下如果一个POI出现在搜索结果里，但是没有任何用户点击，可认为该POI和Query不相关；如果该POI有点击或下单行为，可认为该POI和Query相关。下单行为数据是用户用脚投票得来的，具有更高的置信度，因此我们使用下单数据作为正样本，使用未点击过的数据构造负样本，然后结合业务场景对样本进一步优化。数据优化主要包括对样本去噪和引入品牌数据两个方面。此外，为了评测算法离线效果，我们从构造样本中随机采样9K条样本进行了人工标注作为Benchmark数据集。

样本去噪声：

1.  无意义单字Query过滤。由于单字Query表达的语义通常不完整，用户点击行为也比较随机，如<优，花漾星球专柜（中央大道倍客优）>，这部分数据如果用于训练会影响最终效果。我们去除了包含无意义单字Query的全部样本。
2.  正样本从用户下单的POI中进行随机采样，且过滤掉Query只出现在POI的分店名中的样本，如<大润发，小龙坎老火锅（大润发店）>，虽然Query和POI字面匹配，但其实是不相关结果。
3.  负样本尝试了两种构造方法：全局随机负采样和Skip-Above采样。

1.  全局随机负采样：用户没有点击的POI进行随机采样得到负例。我们观察发现随机采样同样存在大量噪声数据，补充了两项过滤规则来过滤数据。① 大量的POI未被用户点击是因为不是离用户最近的分店，但POI和Query是相关的，这种类型的样例需要过滤掉，如<蛙小侠 ，蛙小侠（新北万达店）>；② 用户Query里包含品牌词，并且POI完全等同于品牌词的，需要从负样本中过滤，如<德克士吃饭 ，德克士>。
2.  Skip-Above采样：受限于App搜索场景的展示屏效，无法保证召回的POI一次性得到曝光。若直接将未被点击的POI作为负例，可能会将未曝光但相关的POI错误地采样为负例。为了保证训练数据的准确性，我们采用Skip-Above方法，剔除这些噪音负例，即从用户点击过的POI之上没有被点击过的POI中采样负例（假设用户是从上往下浏览的POI）。

模型优化

除 query doc 外，还引入 doc 的品类信息，将Doc三级品类信息拼接到Doc标题之后，然后跟Query进行相关性判断。

经过两阶段训练，最终得到一个大的 12 层 BERT 模型。

将该模型进行部署，并通过 spark 任务每周定期对线上疑似地标类 query （ 有地标模型认为有地标意图、有where 成分）的候选召回进行相关性预测，并存入 squirrel 缓存中。缓存中数据量约 6kw 条数据。（失效周期30天）

而后将相关性分数放入 xgb 模型中作为特征输入，最终模型效果提升 xxx。对于没有相关性分数的，采用特殊值填充（2）。
